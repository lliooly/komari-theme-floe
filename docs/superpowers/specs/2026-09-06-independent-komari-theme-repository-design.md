# 独立 Komari 主题仓库与发布基线

## 文档状态

- 状态：已审查通过，进入实施计划阶段。
- 日期：2026-09-06。
- 范围：仓库独立化、来源说明、许可证处理、主题包发布和 Komari themes 上架基线。
- 后续：具体 UI 视觉系统单独立项；本规格不直接实现完整的 UI 重构。

## 背景

当前项目位于 lliooly/komari-next，origin 指向该 fork，upstream 指向原项目 tonyliuzj/komari-next。近期开发已经由本项目维护者独立推进，当前 main 已经包含独立功能提交。

项目的长期定位不再是原项目的同步 fork，而是一个独立维护的 Komari 第三方主题。主题将保留部分来源代码的技术基础，同时逐步建立自己的 UI 语言、交互细节和品牌识别，并通过 Komari themes 发布可安装版本。

## 目标

1. 创建一个与原 fork 网络无关的独立 GitHub 仓库。
2. 保留现有 Git 历史，方便追溯代码来源和维护演进。
3. 在项目说明中明确致敬并引用 Komari Next 原项目及原作者。
4. 保留适用的 MIT 许可义务，同时为本项目新增代码和文档采用兼容的 MIT 许可。
5. 建立可重复的主题构建、Release 和市场上架流程。
6. 让后续 UI 改造围绕一个独立主题身份逐步演进，而不是继续扩展成原项目的替代主线。

## 非目标

- 不修改 Komari 后端、官方主题市场或官方默认主题。
- 不继续定期合并原作者的 upstream。
- 不重写或删除现有 Git 历史中的原作者提交。
- 不在本次规格中确定最终主题名称、Logo、配色方案或完整视觉稿。
- 不在一次变更中完成所有 UI 重构；UI 视觉系统属于后续独立设计周期。
- 不把 /admin 和 /terminal 重新实现为主题自有管理界面。

## 已确认的仓库策略

### 独立仓库作为正式入口

新仓库是之后唯一的正式开发、Issue、Release 和主题市场来源。当前 fork 作为历史迁移源保留，待新仓库完成首个可安装版本后可设置为归档或只读，但不删除历史资料。

迁移时直接将当前 main 的完整历史推送到新仓库，不执行 squash、rebase、filter-repo 或其他会改变提交归属的操作。这样可以同时保留原作者提交、当前维护者提交以及完整的演进脉络。

新仓库的默认分支继续使用 main。日常工作不要求额外创建 dev 分支，也不创建 Git worktree；如未来确实需要独立开发分支，应单独确认分支命名和合并策略。

### Remote 关系

新仓库只配置新的 origin。本地和 CI 配置中不再依赖原作者的 upstream，README、主题 manifest、脚本和工作流也不得继续把原仓库作为更新来源。

原项目只保留为来源说明和兼容性参考，不作为代码同步入口。若 Komari 后端接口或主题规范发生变化，改为根据官方文档、稳定版本和实际安装测试维护兼容性。

## 项目身份与来源说明

README 必须将项目描述为独立的第三方 Komari 主题，避免使用会让用户误认为官方维护或原项目官方分支的表述。建议包含以下信息：

- 本项目是什么主题，以及它的主要视觉方向。
- 本项目部分代码源自 Komari Next。
- Komari Next 原项目地址和原作者信息。
- 本项目之后的 UI、交互和功能调整由当前维护者独立演进。
- 本项目与原项目之间没有持续同步关系。
- 除非另有明确说明，本项目不是 Komari 或原 Komari Next 项目的官方背书版本。

仓库名称、主题显示名称和 short 必须使用独立且不易混淆的命名。首个正式 Release 前必须完成命名，不能继续使用 Komari Next、next 或指向原项目的旧元数据。

当前 komari-theme.json 仍包含原主题名称、原作者、旧版本和 fork 地址。迁移任务必须更新以下字段，并确保仓库内容、主题包和市场目录保持一致：

- name：新主题显示名称。
- short：全局唯一的主题短名称，只使用 Komari 支持的字符。
- description：清楚说明主题定位和主要特色。
- version：从独立主题的版本序列开始维护。
- author：当前维护者或维护团队。
- url：新独立仓库地址。
- preview：主题包内可访问的预览图路径。

README 中原有指向原仓库 Release、预览图和 Star History 的链接也必须迁移到新仓库，不能让用户安装新主题后继续跟随原作者 Release。

## 许可证与归属

当前仓库根目录的 LICENSE 是 MIT License，版权声明属于 Tony Liu。MIT 允许复制、修改、发布和再许可，但要求在软件副本或实质性部分中保留原有版权声明和许可文本。

本项目采用以下规则：

1. 保留现有 MIT License 文本和原版权声明，不删除、不改写成只属于当前维护者。
2. 在 README 的「来源与致谢」章节中补充 Komari Next 原项目和原作者链接。
3. 当前维护者新增的代码、文档和配置继续使用 MIT，前提是这些内容的版权确实属于本项目维护者，且没有引入更严格的第三方许可。
4. 不把 npm 依赖、字体、图标、图片、示例素材或复制来的代码片段自动视为本项目代码；它们必须保留各自的许可证和归属要求。
5. 如果后续引入需要额外归属说明的资源，再增加单独的 NOTICE 或资源归属清单；在没有实际需求前不增加空的许可证文件。

新仓库可以继续使用一份顶层 MIT License，但它不能用来覆盖第三方依赖或删除来源代码的原有归属。发布前需要对新增图片、字体、图标和其他静态资源做一次许可证清单检查。

## 主题架构边界

### 需要保持稳定的 Komari 集成

主题必须继续兼容 Komari 的主题加载方式和前端数据接口，包括：

- 静态导出后的 dist 资源结构。
- 现有 API、RPC、登录和公共信息读取流程。
- 首页、节点详情页、主题配置入口和客户端路由。
- Komari 对页面标题、描述、头部和底部占位内容的替换能力。
- 系统接管的 /admin 和 /terminal 路径。
- 页脚中的 Powered by Komari Monitor.。

UI 改造可以替换布局、组件外观、动效和信息层级，但不能因为视觉重构破坏这些集成边界。

### 自有 UI 方向

后续 UI 工作以一个有明确性格的主题为单位，优先建立以下设计资产：

- 颜色、背景、文字、边框、阴影和状态色 Token。
- 页面容器、导航栏、节点卡片、图表和空状态的统一层级。
- 桌面端与移动端的布局规则。
- 浅色、深色和系统模式下的可读性与状态对比度。
- 交互反馈、加载状态、错误状态和动效节奏。

当前项目已有多配色、卡片布局和图表样式配置。它们可以作为兼容能力保留，但默认值必须体现新主题的主视觉。后续不再无上限增加组合选项；只有能服务主题定位、用户可理解且经过兼容验证的选项才进入主题配置。

## 主题 manifest 兼容性

Komari 当前主题文档使用 configuration.type 和 configuration.data 描述动态配置。managed 类型的 data 是配置项数组，主题设置保存后会通过公共信息接口提供给前端；服务端 1.0.5 及以上支持动态配置，raw 和 redirect 需要更高版本。

当前项目的 komari-theme.json 使用旧的 configuration.managedFields 结构。首个独立 Release 前必须：

1. 对照当前 Komari 主题文档和后端实际版本确认兼容范围。
2. 将动态配置迁移到当前支持的 manifest 结构，或明确验证旧结构仍被目标版本兼容。
3. 保证配置字段的 key、类型、默认值和前端读取逻辑一一对应。
4. 对未声明配置、配置为空、未知字段和旧服务器版本提供安全回退。
5. 不把 Token、密钥或私密 URL 放入通过公共信息接口公开的主题配置。

## 构建、打包与 Release

### 包结构

每个可安装 ZIP 必须在根目录包含 komari-theme.json，并包含 dist 静态资源和预览图。不能把 GitHub 自动生成的 Source code ZIP 当作主题包。

建议的包结构如下：

~~~text
theme.zip
├── komari-theme.json
├── preview.png
└── dist/
    ├── index.html
    └── ...
~~~

构建流程必须在发布前验证以下内容：

- npm run build 成功。
- dist/index.html 保留 Komari 要求的固定 title、description 和 body 占位内容。
- ZIP 根目录存在 manifest，且 JSON 可解析。
- manifest 的 short 和 version 与发布版本一致。
- ZIP 内只有当前主题需要的可安装文件，不混入源码压缩包或其他主题资产。

### 版本与更新

独立主题使用自己的语义化版本序列，不继续沿用原项目的 1.4.x 版本含义。建议在 UI 主题尚未稳定时使用 0.x，第一个稳定视觉基线完成后再发布 1.0.0。

GitHub Release 的版本、主题 manifest 的 version 和市场目录条目必须一致。每个正式 Release 至少提供一个明确命名的主题 ZIP，并计算该 ZIP 的小写 SHA-256。

发布自动化可以继续使用 GitHub Actions，但权限只允许当前仓库构建和创建 Release，不访问或写入原作者仓库。失败时不得创建或更新一个不完整的可安装 Release。

## Komari themes 上架流程

上架前置条件：

1. 新仓库公开可访问。
2. 默认分支和提交作者信息配置正确。
3. 最新 Release 提供可直接安装的主题 ZIP。
4. ZIP 根目录包含 komari-theme.json，manifest、版本和 short 通过校验。
5. 预览图可以通过绝对 HTTP(S) URL 访问。
6. 主题在至少一个实际 Komari 实例中完成安装、刷新、配置读取和更新验证。

提交市场时填写新仓库地址、主题名称、唯一 short、版本、描述、作者和预览图。以 Komari Theme Market 当前仓库的 Issue 模板、校验脚本和工作流要求为准。市场目录保存主题元数据、下载地址和 SHA-256，主题包仍由主题作者自己的 Release 托管。

## 分阶段实施范围

### 阶段 A：仓库独立化与发布基线

本阶段只处理：

- 新建独立仓库并迁移完整历史。
- 设置新的 origin，移除 upstream 依赖。
- 更新项目说明、来源致敬、许可证说明和主题 manifest。
- 确认 manifest 新结构和目标 Komari 版本兼容。
- 建立构建、打包、Release 和 SHA-256 校验流程。
- 发布首个可安装版本并完成市场提交材料。

阶段 A 的完成不以完成全部 UI 重构为前提。这样可以先建立清晰的归属和发布入口，再持续迭代主题外观。

### 阶段 B：主题视觉系统

阶段 B 单独进行 UI 头脑风暴、视觉方向确认和实现计划。每次改动聚焦一个可验证的主题区域，例如导航栏、首页卡片、图表或移动端布局，并在每次 Release 前执行完整兼容性检查。

阶段 B 的 UI 设计不改变阶段 A 已确定的仓库归属、许可证和发布机制。

## 验收标准

### 仓库与归属

- 新仓库不是原项目 fork，且 main 是默认分支。
- 新仓库包含完整历史，历史提交的作者信息未被改写。
- 本地 Git 配置只有新仓库 origin 作为正式发布入口，不依赖 upstream。
- README 明确说明独立第三方主题、来源项目、原作者和后续独立维护关系。
- LICENSE 和新增资源归属说明完整。

### 构建与主题包

- TypeScript 检查和生产构建通过。
- 可安装 ZIP 的根目录包含 komari-theme.json、预览图和 dist。
- manifest 使用目标 Komari 版本支持的结构，short、版本、作者和 URL 正确。
- title、description、body 占位内容和页脚约束未被构建产物破坏。
- ZIP 的 SHA-256 可复现计算，并与发布登记值一致。

### 运行时与市场

- 在目标 Komari 版本中可以安装主题并正常加载首页。
- 浅色、深色、移动端、国际化、节点列表、节点详情和主题设置均可用。
- 主题更新不会继续请求原作者仓库。
- 市场提交信息与 Release manifest 一致，且预览图和下载包可访问。

### 贡献图的预期

新仓库的后续提交只要使用与 GitHub 账户关联的邮箱，并推送到独立仓库的默认分支，通常就满足 GitHub 贡献图的基本条件。迁移后的旧提交是否全部按原日期回溯显示不作为验收条件；历史归属和未来提交可计入应分别看待。

## 风险与取舍

- 新仓库不会自动继承原 fork 的 Star、Issue、Pull Request 和关注关系；这是获得独立身份的可接受成本。
- 保留完整历史意味着原作者提交仍会显示为原作者，不能把来源代码的历史贡献重新归为当前维护者。
- 如果新增资源的许可证不兼容 MIT，必须替换资源或按其要求增加归属和分发限制。
- Komari 主题 manifest 和市场校验规则可能继续变化；发布前以官方文档和市场仓库当前规则为准。
- 每次 Release 都会影响 Komari 的更新检测；正式发布前应区分稳定版本和预览版本，避免把实验性 UI 当作稳定更新推送给用户。
